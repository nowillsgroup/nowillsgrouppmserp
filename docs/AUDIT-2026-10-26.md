# NowillsPMS — System Audit, 26 October 2026

**Audited commit:** `164b4ac` (`main`, the merge of PR #3) · **App version:** 7.56.0
(`config/pms.php`) · **Runtime audited:** PHP 8.4 dev harness (PHP-WASM), SQLite;
production target is PHP 8.4 / MySQL 8 on CyberPanel.

**Verdict: 0 severe. 7 defects found and fixed, nothing left open** — including a
live 500 on a page nobody had opened since the Robita module shipped, and a
cross-tenant staff exposure that reached seventeen call sites. Everything else the
scanner flagged was traced to source and is either a false positive or a
deliberate, documented exception.

---

## 1. How the audit was run

| Layer | What it did |
|---|---|
| **Static** | `deploy/dev/audit/system_audit.php` — parses all **974** PHP files with `token_get_all(…, TOKEN_PARSE)`, balances all **797** Blade views, reads the **2042**-route table, and scans **106** migrations. Rules: syntax, Blade block balance, duplicate route URIs/names, `env()` outside `config/`, migration `down()`/`hasTable()` guards, generated index names > 64 chars, tenant-scoping on hotel-scoped models, staff queries with no hotel filter, raw `{!! !!}`, debug calls, tracked secrets, interpolated SQL, authenticated writes with no `perm:` middleware, `md5` password hashing, doc/version drift, packaging files. |
| **Deployability** | `config:cache`, `route:cache`, `view:cache` all build cleanly, and every page below was re-fetched **with the caches in place** — so no route uses a closure and no runtime code depends on `env()`. |
| **Runtime** | Full GET sweep of every parameter-free route (`deploy/dev/audit/full_get_sweep.py`) plus targeted page checks on the routes touched by the fixes. **This is what caught the `/robita/devices` 500** that the static rules could not see. |
| **Manual** | Every flagged item was opened and read. Nothing in this report rests on a grep count alone. |

Re-run it yourself:

```bash
deploy/dev/bin/php artisan route:list --json > deploy/dev/audit/.routes.json
deploy/dev/bin/php deploy/dev/audit/system_audit.php deploy/dev/audit/.routes.json

```

Exit code is 1 when anything severe is found (CI-friendly). `.routes.json` is a
generated snapshot and is now git-ignored.

## 2. Defects found and fixed

### 2.1 HIGH — an index name MySQL would reject, silently accepted by SQLite

`database/migrations/2026_10_20_006000_create_billing_reconciliation_tables.php:69`

```php
$t->index(['hotel_id', 'document_date', 'document_type']);   // before
```

Laravel generates `billing_reconciliation_items_hotel_id_document_date_document_type_index`
— **71 characters**. MySQL caps identifiers at 64, so this migration fails with
`errno 1059 Identifier name too long` on a fresh production install. SQLite
accepts any length, which is why dev, tests and CI were all green.

**Fixed** with an explicit name (`bcr_items_hotel_date_type`, 25 chars) — the
same convention already used in that file (`bcr_items_hotel_recon_folio`).

*Verified:* created a scratch table in the app with that explicit index name,
confirmed the index list contains `bcr_items_hotel_date_type`, dropped it. Every
other generated index name in all 106 migrations was re-computed against its
own table: the longest remaining is exactly 64 characters
(`channel_room_maps_channel_connection_id_channel_room_code_unique`), which is
legal.

### 2.2 HIGH — `env()` in a service: the SSRF guard silently stops working in production

`app/Services/IcalService.php:156`

```php
$allowPrivate = setting('api_allow_private', '0') === '1' || env('PMS_CHANNEL_ALLOW_PRIVATE');
```

`config:cache` is part of a normal production deploy, and after that `env()`
returns `null` everywhere outside `config/`. The documented escape hatch (both
the `PMS_CHANNEL_ALLOW_PRIVATE=1` variable and, in practice, the Developer →
API “allow private addresses” toggle that falls through to it) is dead in
production — and, worse, a future edit that relies on it would quietly change
SSRF behaviour between dev and prod.

**Fixed** to read the config value that already exists for it
(`config/pms.php:18`):

```php
$allowPrivate = setting('api_allow_private', '0') === '1' || config('pms.channel_allow_private');
```

*Verified:* a whole-repo scan shows this was the **only** `env()` call outside
`config/`. With `config:cache` applied, `/Dashboard`, `/rentals`, `/reports`,
`/hr/ess`, `/learning/sessions` and `/channel-manager/connections` all render
byte-identically.

### 2.3 HIGH — five hotel-scoped models were not tenant-scoped

`app/Models/CarRental.php`, `RentalVehicle.php`, `HrAnnouncement.php`,
`HrDocument.php`, `HrProfileUpdate.php` (new in v7.40, from the PR #3 merge).

All five tables carry `hotel_id`, but none of them used the `BelongsToHotel`
trait, so they had **no global scope and no `hotel_id` stamping**. Consequences:

* `ReportController::r_rental_vehicles()` (line 6359), `r_hr_announcements()`
  (7120), `r_hr_documents()` (7130), `r_hr_profile_updates()` (7140) and
  `r_car_rentals()` (8220) query the models directly, so a report run by Hotel A
  included **Hotel B's fleet, staff documents, staff profile-change requests and
  car-rental bookings**.
* `RentalService::availableVehicles()` (line 60) would offer another property's
  cars for rent.
* Rows created through those paths relied on the writer remembering to set
  `hotel_id` by hand (they do — `RentalService:120`, `EmployeeSelfService:68/136/178`
  are commented “guarded — set explicitly” — but nothing enforced it).

**Fixed:** added `use BelongsToHotel;` to all five models. Checked first that no
group-level query, `withoutGlobalScope('hotel')` or cross-hotel roll-up touches
them, so no intended behaviour is lost.

*Verified at runtime* (inside a rolled-back transaction): a `RentalVehicle`
created while Hotel 1 (NOWILLS) was the tenant was stamped `hotel_id = 1`;
querying the same row as Hotel 2 (NWRESORT) returned **0 rows**; back as
Hotel 1, **1 row**. `/rentals`, `/rentals/fleet`, `/hr/ess`, `/me/announcements`,
`/me/documents`, `/me/hr` and `/hr/register` all still return 200.

### 2.4 LOW — documentation version drift

`docs/INSTALL-CPANEL.md:13` said “Version 7.54.0” while `config/pms.php` says
7.56.0 (the CyberPanel guide already said 7.56.0). Corrected.

### 2.5 HIGH — `/robita/devices` returned HTTP 500 (broken Blade)

`resources/views/robita/devices.blade.php`

The runtime sweep hit one non-deliberate 500: `/robita/devices`. Rendering the
view produced

```
Illuminate\View\ViewException: syntax error, unexpected token "else"
  (compiled view …/views/07f23cc9fd359b109a13b3cabb21772d.php:359)
```

The actions cell ended with an `@else` / `<span class="muted">—</span>` /
`@endif` triple whose `@if` had already been closed by an earlier `@endif` — a
leftover branch from a refactor. Blade compiles `@else` to a bare `else:`, so the
whole page was a PHP syntax error: **the Robita device registry has been
unreachable since the Robita module landed.** Nothing in the static rules or the
`view:cache` step notices this, because compilation succeeds — only *rendering*
fails.

**Fixed** by deleting the dead branch. Every control that matters still renders:
lock/unlock and force-lock/open for online devices, the Reactivate/Decommission
toggle (which must stay visible *for* decommissioned devices), and the event log
link.

*Verified:* `/robita/devices` 200 (361 KB), plus `/robita` (364 KB),
`/robita/events` (353 KB), `/robita/settings` (354 KB).

To stop this class of bug escaping again, the audit tool's Blade rule was
rewritten from an open/close *count* to a **directive stack**: it now reports a
stray `@else`/`@elseif`, `@empty` outside `@forelse`, mismatched `@end…` and
unclosed blocks, and it understands `@hasSection`, `@sectionMissing`, `@isset`
and `@empty($x)`. It flags the pre-fix `devices.blade.php` correctly and reports
the current 797 views clean.

### 2.6 LOW — two PHP 8.4 deprecations on hot paths

`app/Services/RobitaService.php:165` (`KeyCard $card = null`) and
`app/Services/ReservationWorkspaceService.php:101` (`Carbon $date = null`) use
implicitly nullable parameters, deprecated in PHP 8.4 — the runtime the server
uses. Each call logs a `Deprecated:` line, so `laravel.log` fills up the moment
either path is used.

**Fixed** to `?KeyCard` / `?Carbon` (identical semantics). Both were found by a
targeted scan, and a rule for the class was added to the audit tool so new code
cannot reintroduce it.

## 3. Cross-tenant staff exposure — fixed

### 3.1 MEDIUM (was open) — staff pickers were not hotel-scoped

`User` is deliberately **not** tenant-scoped (it is the authentication boundary —
see §4), so every query on it is only safe if it filters `hotel_id` itself. Most
did (20 controllers); these did not, and each was a way for Hotel A to see — or
act on — Hotel B's staff:

| File:line | What leaked |
|---|---|
| `Http/Controllers/InboxController.php:101` | inbox agent list |
| `Http/Controllers/LearningController.php:151`, `:320`, `:327` | trainer list, SOP owner list |
| `Http/Controllers/PettyCashController.php:42` | petty-cash holder list |
| `Http/Controllers/ReportAutomationController.php:83`, `:175` | scheduled-report recipients |
| `Http/Controllers/RequisitionController.php:225` | requisition approvers |
| `Services/InboxService.php:492`, `:830` | agent lookup when assigning / agent names in analytics |
| `Services/LearningService.php:346`, `:631` | **trainer** and **SOP owner** accepted any user id |
| `Services/TalentService.php:254`, `:455`, `:758` | line manager, interview panel, appraisal reviewer accepted any user id |
| `Services/KeyCardService.php:263` | master-key holder lookup |
| `Services/KpiService.php:210` | KPI alert recipients accepted any user id |
| `Services/EmployeeSelfService.php:222` | phone lookup by arbitrary user id |
| `Models/TalentInterview.php:36` | panel names |
| `Http/Controllers/ReportController.php:2466`, `:3444` | “user” filter dropdowns in reports |

More than a display bug: the `findOrFail`/`find` sites accept a **request-supplied
id**, so a crafted POST could assign another property's manager as a trainer, an
interview panellist or an appraisal reviewer, and notifications would follow them.

**Fixed** with one scope on the model — `User::visibleToHotel()` — which returns
the current hotel's staff **plus the group administrators who oversee it**, and
returns the query untouched when there is no tenant (console commands, queue
workers). All seventeen call sites now start from it.

*Verified:* as NOWILLS, the scope returns 28 of 29 users — the only exclusion is
“Resort Manager” (hotel 2, not a group admin); the group administrator is still
returned. User id 29 is now `ModelNotFoundException` for NOWILLS. The trainer,
petty-cash and inbox pickers no longer contain the other hotel's manager, and
`/inbox`, `/learning/sessions`, `/learning/sops/new`, `/accounts/petty-cash`,
`/talent`, `/talent/applicants`, `/key-cards`, `/reports`, `/hr/ess` all render.

The audit tool gained a rule for this class (§7b): an unflagged `User::where/find/
pluck/…` now reports, with `// audit-ok: <reason>` available for the handful of
legitimate cases (recipients already validated when the schedule was saved, a
deactivation aimed at a known employee login, and the pre-tenant login/2FA paths).

## 4. Reviewed and dismissed (reported honestly, with the reason)

| Scanner flag | Verdict | Why |
|---|---|---|
| 108 raw `{!! !!}` outputs | **Safe** | 303 raw echoes in total; all four families were read: (1) QR codes — `$qr`/`EInvoiceService::qrSvg()` are SVG generated in-app from a string we control, never guest input; (2) option/select builders — `gl/mapping.blade.php:6-14`, `contracts/form.blade.php:9` build HTML but run every value through `e()`; (3) number formatters — `$ix` (`bd/*`), `$var` (`owner/_usali`), `money()`, all numeric; (4) CRM campaign preview — `MarketingMail::renderBody()` calls `e()` on the text **before** linkifying, so a `"` in a URL cannot break out of the `href`. Remaining hits are literal markup such as `'<br><span class="note">exp.</span>'`. |
| 6 interpolated SQL statements | **Benign** | `ClubController:350` and `FolioController:38/39` interpolate class constants and `DB::getPdo()->quote()` output; `CrmService:447`, `CroService:484`, `PrivacyService:384` interpolate `locate()`/`?`-bound values. No user input reaches the string. Worth re-reading if those methods are edited. |
| `resources/views/layouts/print.blade.php` “unbalanced Blade blocks” | **False positive** | The view compiles (`view:cache` passes) and prints correctly; the old counter was tripped by `@hasSection`/`@else`. The rewritten stack-based rule (§2.5) no longer reports it. |
| `Services/BackupService.php:9` “`dd()` left in shipped code” | **False positive** | The hit is the docblock bullet `* - full():`; there is no `dd()`/`var_dump`/`print_r` anywhere in shipped code. |
| 9 authenticated writes with no `perm:` middleware | **By design** | `/logout`, `/profile*` (self-service), `/switch-hotel` (checked against `accessibleHotels()`), and `masters.*` (`MasterController:21` gates every call with `abort_unless(can_do($def['perm'] ?? 'masters.manage'), 403)`). |
| `User` has `hotel_id` but no `BelongsToHotel` | **Deliberate** | `User` is the auth boundary: login, password reset and the session guard must resolve a user before a tenant exists, and `switch-hotel` and group administrators legitimately span hotels. Scoping the model globally would break sign-in. Call sites must therefore filter explicitly — `User::visibleToHotel()` is now the sanctioned way do that, and every staff query in the app uses it (§3.1). Keep `User` as the one documented exception. |

## 5. Accepted risks / housekeeping (no action required now)

* **Multi-table migrations guard on the first table only.** 76 migration files
  create several tables behind a single `if (Schema::hasTable('<first>')) { return; }`.
  Re-running is safe as long as the first table is the canary; a database
  restored *partially* (first table present, later ones missing) would skip the
  later tables. Not a live risk on any install we have, and `migrate` tracks
  batches anyway — but new migrations should guard each table.
* **Deferred production items** (previously agreed, unchanged): remove
  `install.php`, add the `schedule:run` cron, set `APP_DEBUG=false` and the real
  `APP_URL`, configure SMTP and backups.
